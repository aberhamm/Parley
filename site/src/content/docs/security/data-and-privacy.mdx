Parley stores very little about people, mostly because it never asks. In its
default mode there is no account, no email address and no password.

## Personal data, in full

| Table | Field | What it is |
|---|---|---|
| `users` | `id` | A generated UUID. Public — it is broadcast to everyone in a room |
| `users` | `name` | Up to 64 characters. Self-chosen, or derived from an identity-provider claim |
| `users` | `issuer`, `subject` | Only for federated sign-in: which provider vouched for you, and your opaque id there. Empty for anonymous users |
| `users` | `avatar_icon` | The avatar you picked, as one short opaque id (≤32 characters). Empty until you choose one. Public — shown to everyone in a room. Removed with the account: it is a column on the `users` row, not a separate record |
| `users` | `avatar_accessory` | Retired in v0.5.1: no longer written or read, and dropped by a later migration |
| `users` | `notification_sounds` | Whether this user enabled local notification sounds. False by default and never included in rosters or session payloads |
| `users` | `created_at` | Timestamp |
| `session_tokens` | `token_hash` | SHA-256 of the bearer token. The token itself is never stored |
| `session_tokens` | `user_id`, `created_at`, `last_used_at` | Which account, and when it was last seen |
| `members` | `space_id`, `user_id`, `spectator`, `last_seen_at` | Which rooms you have joined |
| `session_presence` | `session_id`, `user_id`, `replica_id`, `seen_at` | Which session you have a socket open on, and which replica is serving it. Written while you are connected, deleted when you disconnect, and swept once it ages past the presence window (~100s). It is what the space page counts to say "3 here" |

**No email address is stored**, even when signing in through a provider that
supplies one — an email is used only to derive a display name, and then
discarded. There is **no avatar URL and no uploaded image** — an avatar is a
color derived from your user id plus, optionally, two ids naming a shape you
picked from the built-in set — and **no IP address column** anywhere.

## Content data

Everything else is what a team types: session titles, story titles and
references, notes up to 2000 characters, votes, and standup entries of up to
2000 characters each.

Treat this as the sensitive data. A story note is where somebody writes the
customer's name or the reason a deadline slipped. It is stored as plain text in
Postgres, and it is what a database dump mostly contains.

## What leaves the instance

This Scrum Pro fork includes configured Umami usage analytics through its dedicated
proxy. Do not apply the upstream project's no-analytics claim to this deployment.
Usage analytics, security logs, identity-provider records, downloaded exports and
external integration copies have separate operator retention and erasure controls.
Application deletion does not erase them. No meeting-content erasure guarantee is
made for arbitrary plugin storage or provider copies.

Notification cues are synthesized in the browser with Web Audio. They use no
audio files and make no network request. The server stores only the on/off
preference.

The server connects to configured Postgres. In `open` mode with no webhooks or
network-capable plugins configured, it needs no external service. With
`AUTH_MODE=oidc`, it also contacts the configured IdP for discovery, signing
keys, and sign-in token exchange. Discovery is probed in the background at boot
without gating startup or readiness; a failed probe is retried during sign-in.

Configured standup webhooks send event metadata to their approved recipient;
plugins with approved fetch grants can send requests to allowed HTTPS hosts.
The optional Meet add-on loads Google's SDK in the browser and uses its
activity APIs. Review [Integrations and outbound data](/security/integrations/)
for the current inventory and operator responsibilities. Self-hosting does not
make an external connector or bring-your-own model endpoint local.

## Retention and erasure

Ending a session keeps its history. Signing out (`DELETE /api/me`) revokes only
that sign-in, not the profile or its contributions. Privacy controls are separate
and describe the data they remove from the active application database.

## Boundaries of profile erasure

A historical facilitator or creator UUID can remain on a shared object, pointing
to the immutable, non-login Deleted participant placeholder. Other people's
shared meeting/story text may still mention someone by name; the application
cannot reliably identify or remove those mentions as authored personal rows.
A workspace owner must review shared content separately. An identity provider
can create a fresh account on a future sign-in; it does not recover the erased
account or its hosting permissions. Existing stale credentials and writes must
remain refused after erasure.

Security/audit logs, analytics, exports, backups, external webhooks/provider
copies and arbitrary plugin storage are outside self-service erasure. No promise
of immediate deletion of every copy is made. Do not tell users a fixed backup/log
expiry until the deployment actually enforces and verifies that policy.


## Scrum Pro deployment retention

The Scrum Pro deployment configuration defines a 30-day retention period for
explicitly enrolled encrypted deployment/rollback archives on the application
host and Studio. The NAS has an independent minute job for the exact Scrum
PostgreSQL dump in each dated backup directory, based on its recorded age;
shared tarballs and other applications' artifacts are outside that job.

Private application/DB/gateway/tunnel logs use a separate, root-private syslog
receiver with UTC daily files, size rotation and seven-day closed-file expiry.
Explicitly inventoried historical closed logs use the same seven-day policy.
Active logs are not treated as closed archives. Burst rate limits and
nonblocking buffers can drop diagnostics, and size rotation thresholds may be
exceeded between minute runs. A log file is not a complete audit history.

Expiry occurs on the next successful maintenance pass after a declared
deadline. A scheduled policy is not proof of a successful run during an outage.
Operators inspect host, Studio and NAS status independently. The host exports
deletion receipts each minute, the Studio merges them each minute and mirrors
them to the NAS; this is asynchronous custody with a measurable gap, not a
synchronous off-host guarantee attached to an API deletion response. The two
serial minute phases typically take up to two minutes plus execution/jitter.

Minimal journals are not expired by content policies because they are needed to
reapply deletion after recovery. The former Studio frozen database volume has a
declared expiry of November 20, 2026 at 23:58 UTC; its old container shells and
log caches were removed after verified backup. Protected raw runtime
configuration and signing/encryption keys remain recovery dependencies, with
separately enrolled encrypted config archives. They are not represented as
meeting-content erasure. The operator's 27 October 2026 release record verifies deployment, two-browser
live updates, privacy authorization/erasure, restart persistence, scheduled
journal convergence and a real backup/replay drill. Continued job freshness and
external-copy handling remain operator responsibilities.

## Restoring a backup safely

The minimal deletion journal intentionally retains private identifiers so erased
objects can be removed again after recovery. It must outlive every backup that
could contain those objects. Export/copy failures need operator attention; the
application's successful deletion response alone does not prove the off-host
journal is current. Keep restored writers and outbound effects stopped, verify
instance identity, reconcile historical ownership when necessary, then replay
the journal. Also reconcile permissions and revocations not covered by deletion
receipts before reopening access. See [Backups and recovery](/operations/backups-and-recovery/)
and the repository runbook `docs/privacy-operations.md` for exact commands.


## Protection failure alerts

Scrum Pro's independent operator checker reports backup freshness, host/Studio/NAS
expiry and deletion-journal syncing to Healthchecks every minute. The existing
devops Telegram channel receives failure and recovery notifications. Backups
must be no more than 30 hours old. Maintenance/export/sync success must be no
more than five minutes old; persistent journal/status/mirror divergence gets a
separate five-minute grace to accommodate normal atomic publication gaps.
If the checker itself stops, independent missed-heartbeat alerts trigger about
five minutes after its last successful ping. Only fixed diagnostic codes leave
the checker, not meeting content, personal identifiers or credentials.

The checks are read-only; they do not replace backup restore drills, guarantee
instantaneous off-host custody, or confirm that someone read a notification.
The delivery path depends on the operator's Healthchecks and Telegram services.
Pause the matching checks before intentionally retiring their sender. Runtime
setup, status locations and recovery instructions are in
`deploy/scrum-pro-htz4/README.md` and `docs/privacy-operations.md`.

## Optional Scrum Pro usage analytics

This fork configures coarse page counts only on `scrum.matthew.systems` through
its same-origin analytics gateway. Other deployments and preview hosts do not
automatically use this site. The bundled adapter projects addresses to fixed
categories such as `/workspace` and `/session`; it sends a fixed application
title and empty referrer. Raw organization, workspace and session addresses,
query strings, fragments, names, votes and meeting text are excluded. The
browser projection is data minimization for trusted app calls, not a defense
against someone forging requests to a public collector.

Open **Usage privacy** on any eligible page, including invitation, guest and
presentation pages, to change **Allow usage analytics in this browser**.
Opting out suppresses subsequent sends, and Do Not Track also blocks them.
The preference uses `umami.disabled` in this browser's local storage. If storage
cannot be read, analytics stays blocked until an explicit choice in the open
page; if a choice cannot be saved, the control says so and it applies only to
that document. Enabling may require a reload. The choice does not delete past
analytics or apply to another browser.

Delivery is optional and best effort: unavailable scripts, blocked/offline
requests and ambiguous failures are dropped, without a persistent queue or
automatic replay. Counts describe observed browser actions, not unique people,
meetings or authoritative business records. Expanded named-event collection is
disabled by default pending collector custody and release validation.

When enabled after those gates, explicit successful workspace creation, join,
invitation acceptance, guest-link redemption and session creation callbacks can
send finite action events. Session kind is only `poker`, `standup` or `other`.
Only workspace/session creation refusals and unknown transport outcomes have
error events, with fixed flow/category values and no exception text. Preview,
rendering, existing membership, sign-in prompts and local validation emit no
success event. A repeated acknowledged action may count again; a lost success
response may hide a real creation even when a later retry succeeds. These are
separate observations, not paired attempts or an exact conversion rate.
Navigation failure after acknowledged creation does not change its event.

When separately enabled, ceremony signals count acknowledged local poker votes,
explicit manual reveal requests, the first accepted standup save per mounted
room, and explicit successful closes. Standup close first waits for the last
save; failed saves or denied closes do not count as close success. Room-open
observations require readable built-in room data and a resolved identity.
Receiving live updates, rendering an ended room, automatic reveals and
scheduled actions do not count. No card value, text, participant detail or room
identity is sent. Reloads, remounts, tabs, retries, other devices and blocked
tracking prevent exact people, round, meeting or completion-rate measurements.
Local deduplication lasts only for the mounted room and stores no identifier.
Plugin/unknown rooms and plugin frames remain unobserved.

The operator has accepted a 90-day policy for raw analytics; this is separate
from application erasure and app backup retention. The adapter does not enforce
collector expiry or remove historical analytics. Collector storage, access,
backup exclusion and restore reconciliation require separate operator evidence
before expanded collection is enabled. No anonymity or complete deletion
promise follows merely from the client projection. See the repository's
`docs/analytics/measurement-contract.md` for exact definitions and limitations.
