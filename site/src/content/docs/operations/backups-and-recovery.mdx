The application does not schedule its own database backups. Use `pg_dump`,
encrypt its output, and define operator custody and retention. The optional
generic privacy-maintenance tool expires explicitly enrolled archives without
installing a schedule. The Scrum Pro deployment additionally supplies scoped
host/Studio scheduling and an independent NAS expiry job, described below.

## Back up before every upgrade

Take a dump immediately before every `docker compose up -d` or `helm upgrade`
that changes Parley's version, not just before major ones. Migrations run
automatically at boot, and [some are forward-only with no down
path](/operations/upgrading/#upgrading-to-v050-organizations) — the backup
taken a second before the new version starts is the only way back if a
migration does something you didn't expect.

## Dump it

```sh
docker compose exec db pg_dump -U parley parley > parley-backup.sql
```

## Encrypt the dump

A dump contains meeting content and every space's passcode in readable form.
Session tokens are hashed rather than stored as reusable bearer values, but
restoring their rows can make a previously revoked bearer value valid again.
Plugin, webhook signing and GitHub publication credentials are ciphertext with a separate key
dependency. Treat the dump as a secret from the moment it exists, both at rest
and wherever it travels (object storage, a laptop, an offsite copy).

With [`age`](https://github.com/FiloSottile/age):

```sh
docker compose exec db pg_dump -U parley parley | age -r age1yourpublickeyhere > parley-backup.sql.age

# restore
age -d -i key.txt parley-backup.sql.age > parley-backup.sql
```

With `gpg`, symmetric encryption uses a passphrase, which still needs protected
recovery custody:

```sh
docker compose exec db pg_dump -U parley parley | gpg --symmetric --cipher-algo AES256 -o parley-backup.sql.gpg

# restore
gpg --decrypt parley-backup.sql.gpg > parley-backup.sql
```

Either way, keep the passphrase or private key off the machine that holds the
dump — an encrypted backup sitting next to its own key protects against
nothing.

## Preserve the recovery dependencies

Record the backup's timestamp, database/schema and Parley versions, configured
plugins/bundles, and key IDs needed to read encrypted secrets. Keep the matching
`PLUGIN_SECRET_KEY` and, where needed during rotation,
`PLUGIN_SECRET_KEY_PREVIOUS` in separately protected recovery custody. These
environment secrets are not included in `pg_dump`. Older backups may need an
older key even after all live rows have been resealed; retain the necessary
key material for the permitted backup lifetime, with restricted access.

Also preserve the dump-encryption key, deployment configuration, trusted plugin
signer keys/bundles, and IdP/TLS dependencies. Record who may retrieve each
dependency and how access works if the normal host or IdP is unavailable.
Do not put keys into the evidence register or next to a broadly readable dump.

Without a matching key, restoring the database does not recover plugin or
webhook secrets. Re-enter or rotate affected provider/signing credentials
through supported configuration after recovery; a fresh key cannot decrypt old
ciphertext. Review [plugin key rotation](/operations/plugins/) before removing
an old key.

## Restore it

Into a fresh stack:

Keep every Parley replica stopped and start only Postgres for the restore and
reconciliation below. Keep ingress and outbound effects restricted through
validation. Set those network restrictions **before** starting Parley. A scratch
restore must not send queued plugin jobs or webhook deliveries to production
recipients.

Parley has no worker-pause configuration: starting the server also starts its
queue and outbox workers. Network isolation alone cannot prevent queued plugin
jobs from changing local state under restored grants or consuming delivery
attempts.

```sh
docker compose up -d db
cat parley-backup.sql | docker compose exec -T db psql -U parley parley
```

## Reconcile access before reopening

A backup also rolls authorization and queues back to its timestamp. Compare it
with protected records of subsequent account/membership removals, org
revocation tombstones, token and signed-link revocations, plugin grant changes,
connector removals, and deletions. Reapply those decisions while only Postgres
is running, before starting any Parley replica. If there is no reliable change
record, choose a conservative reset of affected sessions/links/credentials and
require renewed authorization;
do not assume the restored state is current.

Deleting restored session-token rows alone does not prevent a restored active
signed link from minting another token. Reconcile links as well as tokens,
membership and grants. Review pending outbox/jobs and webhook deliveries for
stale authority and duplicate effects, and resolve queued work that must not
run, while Parley is still stopped. Confirm that the configured keys can
decrypt retained secrets before any delivery is attempted.

Restoring can also resurrect deleted content. Apply the deployment's retention
and deletion decisions to live records and recovery copies, and document any
remaining backup-retention limits. Parley does not supply automatic
post-restore reconciliation; the operator owns this procedure.

After database reconciliation, start all replicas against the reconciled store
with the network restrictions still in place:

```sh
docker compose up -d
```

Verify old HTTP and WebSocket credentials and revoked link redemptions are
refused before reopening access or egress.

:::danger[down -v deletes your data]
`docker compose down -v` removes the data volume: spaces, estimates, standup
history, all of it. Plain `docker compose down` is safe.
:::

## On Kubernetes

`pg_dump` still does the job, but nothing runs it for you. Schedule it as a
`CronJob` in the same namespace that execs into (or connects directly to) the
Postgres pod/service and writes the encrypted dump to object storage — the
[Kubernetes](/operations/kubernetes/) page and your Postgres operator's own
docs (CloudNativePG, Zalando, Crunchy) are the right starting point, since the
exact command depends on which one manages your database. If you run your own
Postgres StatefulSet rather than an operator, the CronJob runs the same
`pg_dump | age` pipeline above from a pod instead of a laptop.

## Run a restore drill

A backup you have never restored is a hope, not a backup. Periodically:

1. Spin up a scratch stack (a second Compose project or a throwaway
   namespace).
2. Restore the most recent dump with only Postgres running, then reconcile
   post-backup authorization, deletions, and pending queues before starting
   Parley.
3. Start Parley with network restrictions in place. Confirm the app boots
   against it and a space you recognize is there.
4. Check representative sessions, votes/entries, plugin state, and encrypted
   secrets with the matching recovery keys. Confirm post-backup revocations
   and deletions have been reconciled, and old credentials/links are refused.
5. Record the tested backup age, versions/digest, key availability (no key
   values), data/access checks, elapsed recovery time, failures, owner and date.
   Compare the result with your chosen RPO/RTO.
6. Tear the scratch stack down, including its sensitive recovered data.

Do this after any schema-changing upgrade, not just on a calendar — that's the
moment a restore is most likely to surface a problem while it's still cheap to
find one.

## What this shape actually recovers

A `pg_dump` backup has a bluntly honest RPO/RTO, worth stating rather than
assuming:

- **RPO (how much you can lose)** is the interval between dumps. A backup
  taken once a day means up to a day of standups, estimates, and roster
  changes are gone if you have to restore. Dump more often if that's not
  acceptable — nothing in this shape requires daily.
- **RTO (how long you're down)** includes provisioning, retrieving and
  decrypting the backup, restoring the database and keys, reconciling access
  and deletions, validating the result, and reopening the service. Measure it
  in a representative drill; database size and an unprovisioned target can
  dominate it. Set an objective from your deployment's needs rather than
  treating an estimated restart time as a recovery commitment.

Point-in-time recovery, replication, and continuous WAL archiving are real
options if this RPO isn't good enough, but they are a Postgres operations
topic in their own right and outside what this page covers — they layer on
top of the same `parley` database this page backs up.


## Publication credentials after restore

GitHub publication credentials use the existing current/previous keys and
`parley secrets reseal`. Ciphertext always binds connection ID, org, space,
room and principal; legacy unbound ciphertext is refused even in recovery.
The dedicated table participates in stale counts, compare-and-set reseal and
the final locked check. Corrupt or wrong-scope rows prevent zero-remaining
recovery; re-enter or revoke them before removing the previous key.

A restored backup may restore a removed PAT connection or old grants. Before
exposure, reconcile membership, facilitator and connection revocations against
post-backup changes, and revoke the upstream token when needed. Keep delivery
paused until scope and keys are checked. Reconcile retained unknown identities
against GitHub rather than clearing or recreating them. Never put reusable PATs
in support artifacts, exports or restore logs.


## Scrum Pro deletion recovery and expiry

Migration 0061 adds minimal transactional deletion receipts and a stable database
instance UUID. Before exposing a restored store, export/copy the latest private
journal independently of the backup and replay it with all writers stopped.
The cumulative journal must outlive any backup that can resurrect its records.
Wrong-instance files and unresolved historical owner/admin handoffs fail closed.
Receipts cover deletion, not every permission revocation or external effect.

`scripts/privacy-maintenance.py export --journal <private-file>` atomically
merges receipts into a 0600 journal. `replay --journal <private-file>
--writers-stopped` validates and replays in one database transaction. A successful
live deletion is not evidence that the later off-host journal export succeeded.
Track that export/copy boundary. Historical backups predating the privacy metadata
require verified operator reconciliation, not automatic adoption of a new UUID.

The same tool supplies dry-run-first expiry for exact manifest-owned encrypted
backup/rollback archives and closed JSON or explicitly renamed `.archived.log`
archives. `--apply` is explicit;
checksums, UTC expiry, ownership, file types and link/path protections are checked
before deletion. The generic CLI alone does not install scheduling or provide a
blanket erasure guarantee. See `docs/privacy-operations.md` in the
repository for the manifest schema, commands, boundaries and recovery procedure.


### Scoped Scrum Pro deployment policy

The deployment supplies `scrum-pro-logging.service`, a dedicated private syslog
receiver, plus `scrum-pro-privacy-maintenance.timer` every minute for cumulative
journal export, private logrotate and expiry. Logging uses RFC5424 APP-NAME
filtering, 0700/0600 custody, seven-day closed UTC files, three rotations and a
10 MiB rotation threshold. Nonblocking/burst limits can drop messages; the
threshold can be exceeded between runs. The host's encrypted backup inventory
uses exactly original creation plus 30 days.

The Studio LaunchDaemon `com.matthew.scrum-pro-privacy` runs each minute, checks
source checksum/instance/count/freshness, cumulatively merges the journal and
mirrors it to private NAS custody. Host export and Studio pull are serial minute
phases, typically up to two minutes plus execution/jitter end to end. Known
Studio encrypted archives have a
30-day policy, historical `.archived.log` files have seven days, and a failed
pull does not extend an already-enrolled local artifact's expiry. Journals are
not subject to content expiry and must outlive recoverable older content.

An independent NAS root cron runs every minute for the exact
`htz-4g-nbg/<dated-directory>/scrum-pro-parley.dump` only. It uses the file's
recorded mtime for its 30-day cutoff, validates the private custom-format file
and its identity before unlinking, and leaves shared config archives, other
apps' files and snapshot directories untouched. A failed host export or Studio
pull does not suspend this independently scheduled NAS dump expiry.

These are scheduled policies, enforced on the next successful pass after a
deadline. Inspect source-export, Studio sync/expiry and NAS expiry status
separately. Before reopening a restored store, obtain the latest complete
independent journal and replay it with writers stopped. The privacy release
requires schema 63; a pre-privacy schema-60 image is not a compatible recovery
binary. Restoring a pre-upgrade dump still requires a compatible migration path
and the latest erasure/permission reconciliation before any public access.

The former Studio container shells and log caches were removed after verified
backup. Its frozen rollback volume is enrolled to expire November 20, 2026 at
23:58 UTC. Raw signing/key-recovery runtime configuration remains protected
custody; its encrypted legacy configuration archives have separate 30-day
expiry. This distinction is not a promise to erase every configuration/key
copy or physically sanitize storage media. See `docs/privacy-operations.md`
and the deployment README for exact custody paths and commands. The 27 October 2026 rollout record verifies live privacy QA, restart
persistence, scheduled five-receipt journal convergence and a real restored
production snapshot reconciled through the automatically synced journal, with
idempotent replay and unrelated data preserved. A new off-host postdeploy backup
was fully restored at schema 63. These executed checks do not prove every future
maintenance run or a host reboot recovery drill.


## Protection failure alerts

Scrum Pro's independent operator checker reports backup freshness, host/Studio/NAS
expiry and deletion-journal syncing to Healthchecks every minute. The existing
devops Telegram channel receives failure and recovery notifications. Backups
must be no more than 30 hours old. Maintenance/export/sync success must be no
more than five minutes old; persistent journal/status/mirror divergence gets a
separate five-minute grace to accommodate normal atomic publication gaps.
If the checker itself stops, independent missed-heartbeat alerts trigger about
five minutes after its last successful ping. Only fixed diagnostic codes leave
the checker, not meeting content, personal identifiers or credentials.

The checks are read-only; they do not replace backup restore drills, guarantee
instantaneous off-host custody, or confirm that someone read a notification.
The delivery path depends on the operator's Healthchecks and Telegram services.
Pause the matching checks before intentionally retiring their sender. Runtime
setup, status locations and recovery instructions are in
`deploy/scrum-pro-htz4/README.md` and `docs/privacy-operations.md`.
